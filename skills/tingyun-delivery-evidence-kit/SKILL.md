# 虚拟商品交付履约凭证助手

## 一、这个技能解决什么问题

虚拟商品卖家的真实成本，往往不在纠纷本身，而在**举证不能**。买家拿到手说"跟你说的不一样"，卖家翻遍聊天记录只能回一句"我发给你的就是这个"，双方都拿不出可核对的东西，最后平台按"虚拟商品无有效证明"处理：卖家退款，买家骂人，下一个买家继续担心。

虚拟商品投诉里有一批反复出现的共同根因——**买家收到货后无法证明卖家给的和说的一致**。买家最常见的说法是：

- "24章节的内容只有6章" → 缺件数核对
- "口诀只有35条，剩下的以其他资料滥竎充数" → 缺条数核对
- "重点加上习题一共就30页，只列问题让自己整理答案" → 缺交付形态说明
- "商品采用网盘链接自动发货，但详情页没有显著提前告知必须使用百度网盘才能下载" → 缺前置条件告知
- "均未以任何形式标注或告知该下载链接的有效期限" → 缺有效期
- "卖家单方面取消网盘分享链接，直接切断我获取商品的渠道" → 缺交付存续承诺

这六句拆开是六个各自独立、互不替代的举证缺口：件数、条数、形态、前置条件、有效期、存续承诺。任何一环缺失，"我发的就是这个"都站不住。

所以这个技能不是"生成一个好看的凭证"，它要做的是**把承诺与交付变成可以逐项核对的数字**，让买家能自证、让卖家能免责、让平台有据可依。

## 二、适用与不适用

**适用**：卖虚拟资料、模板、素材、试卷、教程、服务类交付的个体卖家与小商家；退款率偏高且投诉集中在"货不对板"的店铺；交付形态为网盘链接、在线文档、邮件附件等一次性交付；需要把流程标准化、新人也能照做的团队。

**不适用**：

- **实物商品**。实物有物流单号、开箱记录、退货签收链路，举证方法完全不同。
- **替代平台自带的虚拟商品机制**。平台若已提供官方虚拟发货凭证与售后流程，以平台机制为准。
- **内容创作、选题、定价、投流**。只管交付环节。
- **判断纠纷责任归属**。凭证只证明"交付了什么"，不证明"谁违约"。
- **规避平台审核或伪造凭证**。校验值必须来自真实文件，本技能不提供任何变造、隐藏交付记录的方法。

**关键立场**：这套东西是给双方降低成本的，不是给卖家逃避责任的。规则文本一律保护消费者一侧。

## 三、四层凭证结构

**第 1 层 · 承诺层：商品页承诺与交付物对照**
把详情页每条承诺抄成清单，写成可点数的句子。这一层回答"卖家承诺了什么"，是后面三层的锚点。

**第 2 层 · 清单层：逐项文件 + 件数 + 页数**
每个交付文件一行，记文件名、格式、页数或条目数、备注。直接堵住"24章只有6章"这类件数争议。

**第 3 层 · 校验层：校验值 + 版本号 + 时间戳**
每个文件算 SHA-256（展示前 16 位即可），配交付版本号与时间戳。校验值回答"我手上的东西，是不是你当初发的那一份"——文件被替换、截断、换成占位文件，校验值都会变。版本号区分"补发前"与"补发后"。

**第 4 层 · 确认层：买家确认与留痕**
买家核对后回一句确认（不必走繁琐流程）。确认不是强制的——未确认不影响买家法定权利——但确认过的订单，卖家举证成本明显下降。

四层是递进的举证链：承诺层定义事实，清单层固定事实，校验层证明完整性，确认层锁定双方认知。

## 四、八步交付 SOP

| 步骤 | 动作 | 产物 |
| --- | --- | --- |
| 1 · 抄承诺 | 把详情页每条承诺抄进表，写成可点数句子 | 承诺清单 |
| 2 · 定口径 | 明确页数、条目数、文件数的统计方式 | 口径说明 |
| 3 · 打包 | 一个承诺一个文件；禁止混入占位文件 | 打包目录 |
| 4 · 算校验 | 逐文件算 SHA-256，统计文件数、页数、条目数 | 交付清单 CSV |
| 5 · 核承诺 | 逐条比对，缺件直接暴露，不做静默通过 | 核对结论 |
| 6 · 写规则 | 选定退换策略，生成规则文本 | 规则文本 |
| 7 · 出凭证 | 合成买家可见的《交付凭证》 | 凭证页 Markdown |
| 8 · 留存归档 | 消息、凭证页、清单一起存档，版本号与时间戳对齐 | 交付档案 |

脚本一次跑完第 4 至 7 步：

```bash
python scripts/delivery_evidence.py --input delivery.json --json
python scripts/delivery_evidence.py --input delivery.json --out ./输出目录
```

`--json` 输出结构化结果，含 `findings` 列表（每条含 level / wording / suggestion）；`--out` 写出"交付清单.csv"与"交付凭证.md"。脚本只依赖 Python 标准库。

## 五、可核验数字原则

**能点数的就别形容。**

| 弱写法（纠纷高发） | 强写法（可核对） |
| --- | --- |
| 全套资料 / 资料大全 | 含 6 张体检表、8 页使用说明、30 道配套练习题 |
| 24 章节的完整内容 | 24 章 = 96 节，每章 4 节 |
| 口诀 35 条 | 口诀 35 条（附件《口诀速记.txt》，共 2 页） |
| 重点 + 习题 | 重点部分共 30 页，含 20 道习题与 10 页要点解析 |
| 精讲版 | 精讲视频 12 节，每节约 15 分钟，附字幕文本 |
| 附赠案例库 | 附赠案例库 20 例（PDF，18 页），单独文件交付 |

**为什么"全套 / 大全 / 精讲"是纠纷高发词**：这些词没有边界，双方理解必然不同。买家按"全套"理解为全部内容，卖家按"全套"理解为自己手上那一版。差异在交付瞬间就已存在，只是平时没人去数，一旦买家数了，退款理由就成立。**模糊词不是销售语言，是未结算的债务**。

三条替换规则：承诺句里至少出现一个数字；统计口径写进商品页（"6 张表"指工作表还是图片？）；多给的也要写明，避免买家怀疑剩下的是凑数的。

## 六、交付前 15 项自检清单

完整版（每项含检查项 / 怎么查 / 不通过后果 / 通过标准）见 `references/fulfillment-checklist.md`，可直接打印勾选：

1. 承诺句全部可点数，无模糊描述词
2. 统计口径（表 / 题 / 页 / 条）已写入商品页
3. 承诺条数与交付文件一一对应
4. 每个承诺都能在交付物中找到对应项
5. 件数与承诺完全一致，无缺件
6. 页数与承诺一致，且经阅读器确认
7. 条目数（题 / 条 / 章）与承诺一致
8. 交付形态已写明（是否含答案、是否可打印、是否需自行整理）
9. 前置条件已告知（下载工具、账号、格式要求）
10. 下载有效期已明确标注
11. 交付存续承诺已写明（到期不静默取消、提前提醒）
12. 无 0 字节空文件、无占位文件
13. 版本号已设定且与本次交付对应
14. 存在使用说明或目录文件
15. 退换规则已选定，且文本保护消费者一侧

每项必须能回答"通过 / 不通过"。回答"不确定"的按不通过处理。

## 七、边界与免责

1. **不构成法律意见**。输出仅为交付管理的辅助材料，不构成法律意见或责任认定。
2. **不替代平台规则**。平台规则以平台当期公示为准；本技能不引用具体条款编号。
3. **不承诺纠纷一定胜诉**。凭证提高举证能力，不决定平台或司法判断。
4. **不处理实物商品**；**不替代平台官方虚拟发货机制**。
5. **不教规避审核、不教伪造凭证**。校验值必须来自真实交付文件。
6. **不评价内容质量与教学效果**。只核对交付形态与件数。
7. **不代替人工复核**。凭证页与规则文本发出前必须人工过一遍。
8. **数据不外传**。脚本本地运行，不联网不上传。
9. **示例数据均为占位示例**，不含真实姓名、联系方式或交易信息。

## 八、常见问答

**Q1：文件我确实都发了，为什么还被投诉？**
"发了"和"买家能确认收到的是完整的"是两件事。缺件、形态不符、前置条件未告知这三类投诉，卖家手上通常只有一句"我发了"。清单加校验值把这句话变成可核对的数字。

**Q2：算校验值麻烦吗？**
交付一次算一次，几秒，脚本一次跑完。真正贵的不是这几秒，是反复返工补发和差评。

**Q3：买家不肯确认回执怎么办？**
不影响。确认层只是加分项，未确认不影响买家法定权利，也不影响缺件永久补发。规则文本里已写明。

**Q4：买家已下载、也确认过，还是说货不对板？**
先分清是"数量/形态不符"还是"主观不满意"。前者按缺件永久补发处理，凭证就是底气；后者多半是商品页过度承诺，该改的是描述。

**Q5：网盘链接有效期定多少合适？**
常见做法 30 到 90 天。关键不在天数，而在**必须写明**、**到期前主动提醒并延长**。买家常投诉的不是有效期本身，而是"没告知期限"和"到期直接切断"。

**Q6：卖的是长期答疑服务，还要凭证吗？**
要，但形式不同：每次更新的版本号、时间戳、更新内容清单仍然要留，因为"这次更新包含什么"最容易说不清。有效期改为"服务期截止日"。

**Q7：脚本会把我的文件传出去吗？**
不会。只用 Python 标准库，本地读文件算 SHA-256，不联网。

**Q8：商品页已写"全套"，改会影响销量吗？**
短期可能，长期一定划算。模糊写法带来的退款与差评通常远超转化损失。折中做法：标题保留卖点词，正文用可点数的句子展开承诺。

**Q9：对方要求"能证明商品完好的凭证"，发什么？**
《交付凭证》页 + 交付清单截图 + 交付消息记录。三者一起：凭证页说明交付内容，清单说明件数，消息记录说明时点与渠道。

**Q10：中途买家让我补发，怎么证明补发的是原件？**
补发时同步升版本号，重出清单与校验值，注明"本次补发对应原承诺第 X 条"。补发记录本身就是最好的证据。

## 九、给 Agent 的调用说明

```bash
python scripts/delivery_evidence.py --input delivery.json [--json] [--out 输出目录]
```

输入 `delivery.json` 结构：

```json
{
  "order": {"no": "20261101-XY-001", "platform": "闲鱼", "product": "家庭保单体检表", "price": 19.9},
  "seller": {"name": "示例工作室", "contact": "示例联系方式"},
  "files": [
    {"path": "打包内容/保单汇总表.xlsx", "pages": 1, "items": 6, "note": "含 6 个表"},
    {"path": "打包内容/使用说明.pdf", "pages": 8, "items": 0, "note": ""}
  ],
  "commitments": ["商品页承诺：含 6 张体检表", "商品页承诺：附使用说明"],
  "delivery_channel": "网盘链接",
  "prerequisites": "需使用百度网盘客户端下载",
  "valid_days": 30,
  "version": "v1.2",
  "refund_policy": "not_downloaded_refundable"
}
```

调用要点：`commitments` 逐条录入商品页原话，不要改写成漂亮说法——脚本比对的就是原话；`files[].path` 相对 `delivery.json` 所在目录解析，也可写绝对路径，文件不存在会报 error 级问题；`files[].pages` 填页数，`items` 填条目数，`note` 写清该文件装了什么；`refund_policy` 取值 `not_downloaded_refundable`（未下载可退）/ `downloaded_no_refund`（已下载不退）/ `missing_permanent_resend`（缺件永久补发），多个用 `+` 连接；`findings` 中 `level` 为 `error` 的条目必须先处理再交付；文件不存在或 JSON 非法时脚本输出友好提示并以退出码 2 结束。

配套文档：`references/fulfillment-checklist.md`（15 项自检 + 清单模板 + 凭证页模板 + 3 版退换规则 + 高风险类目红线）、`references/dispute-playbook.md`（12 类纠纷处置手册）。
